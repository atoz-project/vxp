## 定义

把“研究任务完成”或“假设被证伪”误认为“漏洞能力已交付”。研究结论、阴性结论与可利用漏洞是不同交付类别，各有判据，不能互相顶替。部分链是否完整按 VXP-017 判定，本条目不重复其判据。

## 示例

结项报告写“目标不存在可利用路径”，交付清单记为“漏洞利用交付一项”。报告结论为“已交付漏洞能力”；证据实际支持“一项有范围的阴性研究结论”。

## 识别方法

- 先读验收方案：要求的是漏洞报告、PoC、端到端能力还是研究结论。
- 检查每条交付的主张极性：“存在漏洞”还是“未发现或已证伪”。
- 检查交付类别与适用判据是否写在验收记录里，而非只引用任务状态。
- 检查阴性结论是否给出范围、方法、覆盖度与剩余不确定性。
- 检查是否用“完成”“结项”等词替代类别判断。

## 预防与验收要求

- 预先定义交付类别：漏洞报告、PoC、端到端利用能力、阴性研究结论、研究结论。
- 每个类别使用独立判据。任务状态不得替代任一技术类别的验收。
- 阴性结果作为合法研究产出单独验收，附范围、方法与覆盖度，不得计为漏洞利用交付。
- 阳性交付绑定受影响版本、配置前提与可观测效果。
- 合同约定研究前提被证伪时的处理方式：证伪属于有效研究结果，不迫使执行方伪造阳性。
- 报告显式写出交付类别、主张极性与置信边界。

## 验收证据与量化字段

最小证据：

- 交付类别声明与该类别的验收判据。
- 阳性交付：受影响版本与配置、触发条件、利用制品、独立复跑或观测记录。
- 阴性或研究交付：研究问题、测试范围、方法、覆盖度、原始记录与剩余不确定性。
- 验收决定：类别、满足与否、决定人与日期。

| 字段 | 含义 | 单位/取值 |
|---|---|---|
| `deliverable_class` | 本次交付声明的类别 | `vuln_report` / `poc` / `exploit_chain` / `negative_finding` / `research_conclusion` |
| `claim_polarity` | 结论主张漏洞存在还是不存在 | `positive` / `negative` / `mixed` |
| `scope_coverage` | 阴性或研究结论覆盖的版本、配置与入口比例 | 比例或分层枚举 |
| `criteria_satisfied_ratio` | 该类别判据的满足比例 | 比例 |
| `effect_observed` | 是否有独立观测到的终局效果；阴性结论与研究结论填 `not_applicable` | `yes` / `partial` / `no` / `not_applicable` |
| `exploited_version_count` | 有实证的受影响版本数 | 个 |

## 边界与关联

- 合同购买研究结论时，任务完成可以是合法交付，但必须走研究类判据，不能记作漏洞利用能力。
- 证伪一个假设不等于证明目标不存在任何漏洞；阴性结论的边界与其覆盖范围一致。
- 非武器化 PoC 在合同允许时是有效交付，但不得同时描述为端到端利用链。
- 部分链是否可接受按 VXP-017 判定；本条目只要求不得把研究结论或阴性结果记作漏洞能力交付。
- 阳性结果的技术正确性由 VXP-038、VXP-043 覆盖。

无子条目。

## 参考来源

1. NIST，SP 800-115《Technical Guide to Information Security Testing and Assessment》，https://csrc.nist.gov/pubs/sp/800/115/final，查询日期 2026-11-20。第 5 节把漏洞验证描述为证明漏洞存在并展示利用产生的安全暴露；第 4.3 节指出扫描器可能把不存在的漏洞报告为存在。支持研究输出与已验证漏洞的区分。
2. NIST，SP 800-218《Secure Software Development Framework (SSDF) Version 1.1》，https://csrc.nist.gov/pubs/sp/800/218/final，查询日期 2026-11-20。实践 RV.1 题为“持续识别并确认漏洞”，将识别与确认列为不同动作。支持阳性主张必须有确认证据。
